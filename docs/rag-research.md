# Chat with PDF: retrieval scalability research

Checked 2026-09-27 against the [official template](https://mastra.ai/templates/chat-with-pdf), its [source repository](https://github.com/mastra-ai/template-chat-with-pdf), Mastra documentation, and pgvector documentation. This is an architecture assessment, not a measured benchmark of this project.

The workspace now presents this retrieval system as a thesis and capstone literature review tool. Papers belong to research projects, queries are filtered by project ID in the vector search, and evidence notes resolve to stored source chunks. OpenAlex discovery supplies metadata and candidate PDF links. These changes do not constitute a measured large-corpus performance result.

## What the upstream template does

- PDF URL ingestion extracts text page by page, chunks each page recursively at `maxSize: 512` with `overlap: 50`, embeds with `openai/text-embedding-3-small`, and stores chunks plus document and page metadata in one local LibSQL vector index. On reingestion it deletes vectors filtered by `documentId`, then upserts the replacement chunks. See the [upstream workflow](https://github.com/mastra-ai/template-chat-with-pdf/blob/main/src/mastra/workflows/index-pdf.ts).
- Ordinary queries run a single dense similarity search with `topK: 20` and optional `documentId` filter. A page range triggers several page-filtered queries for randomly sampled pages. This sampling can miss an answer on an unselected page and the number of queries grows with selected pages. See the [upstream query tool](https://github.com/mastra-ai/template-chat-with-pdf/blob/main/src/mastra/tools/pdf-query-tool.ts).
- Document listing uses an arbitrary embedding and `topK: 1000` vector search, then deduplicates returned chunk metadata. Its own source notes that it may omit documents once the corpus exceeds 1,000 chunks. See the [upstream listing tool](https://github.com/mastra-ai/template-chat-with-pdf/blob/main/src/mastra/tools/list-documents-tool.ts). This is the first concrete scale bug to fix.

## Changes made in this workspace

- Replaced vector-search document listing with a paginated PostgreSQL document registry. The updated tool no longer needs an embedding call or a `topK: 1000` limit.
- Replaced the URL-suffix document ID with a SHA-256-derived ID and added document ID and URL to ordinary retrieval results for clearer cross-document citations.
- Replaced random page sampling with one metadata-filtered vector query over the requested page range. This removes omitted pages from the search scope, though `topK: 20` still bounds returned results.
- Moved vector and Mastra storage to PostgreSQL/pgvector, configurable with `DATABASE_URL`. Index creation explicitly requests cosine HNSW (`m=16`, `ef_construction=64`). The project-scoped research query uses `ORDER BY embedding <=> query LIMIT k` with `ef_search=100` and iterative scanning. This direct SQL shape is important: the installed Mastra PgVector adapter's filtered query orders computed scores after a materialized candidate step and is not an HNSW nearest-neighbor scan. A local database catalog check confirmed the physical `USING hnsw` index. With sort plans disabled for plan inspection, PostgreSQL showed the filtered query can take the HNSW index path; with the current empty corpus and normal planning, it instead chose the project metadata index. The React frontend reports index presence, not a measured speedup.
- Added project-scoped research retrieval, a scholarly discovery adapter, and an evidence matrix whose saved quotes are fetched from indexed source chunks. The project filter is enforced by the application query, not left to an agent prompt.
- These changes are a foundation, not a claim of production-scale retrieval. The query path is still dense-only; indexed documents are not yet represented as parent/section/leaf records. No large-corpus retrieval benchmark has been run.

## Terms that matter

**Hierarchical RAG** means searching a coarse level (for example document or section summaries), then searching or expanding fine chunks within selected parents. It is an application retrieval design; the template does not implement it. It can reduce candidate scope and improve document-level recall, but an early coarse-stage miss can also hide the right child. A parent-child link and durable source text are needed for expansion. Mastra supplies chunking, embeddings, vector queries, filters, and workflows from which to build it; its [RAG overview](https://mastra.ai/reference/rag/overview) describes these primitives.

**HNSW (hierarchical navigable small world)** is a multilayer graph index for approximate nearest-neighbor vector lookup. It accelerates candidate search; it does not create document/section hierarchy or improve semantic understanding by itself. pgvector describes the speed–recall tradeoff and its `m`, `ef_construction`, and `ef_search` settings in the [official pgvector README](https://github.com/pgvector/pgvector#hnsw). The implemented index uses [Mastra's PgVector `createIndex` API](https://mastra.ai/reference/vectors/pg).

**Mastra GraphRAG** is a third pattern: vector retrieval plus relationship traversal, intended for facts connected across documents. Its [guide](https://mastra.ai/reference/rag/graph-rag-guide) builds a graph from retrieved chunks. It is not equivalent to HNSW or parent-child retrieval, and is not the first performance fix for many independent PDFs.

## Recommended order for thousands of PDFs

1. **Finish corpus management and safety.** The registry and collision-resistant IDs are now in place. Add version or content hash, job status, tenant/access scope, and stable chunk IDs. Make indexing idempotent and track failed or partial jobs. Mastra documents [`deleteVectors` by document metadata filter](https://mastra.ai/reference/rag/vector-databases#deleting-vectors) for cleanup; deletion, registry state, and reingestion need to be coordinated by the application.
2. **Constrain every search before tuning ANN.** Apply tenant/permission and user-selected document filters at query time, then corpus metadata such as source, type, section, and date where useful. Mastra's [metadata filter API](https://mastra.ai/reference/rag/metadata-filters) provides a common syntax, although operators and performance differ by backend. For Postgres, Mastra added `metadataIndexes` to create btree indexes on filtered metadata ([changelog](https://mastra.ai/blog/changelog-2026-03-16)). Never rely on agent instructions alone to enforce access scope.
3. **Measure and tune the pgvector backend.** PostgreSQL and HNSW are implemented locally. Hosted deployment can use the same code with a new `DATABASE_URL`, but concurrency, backups, memory, and index maintenance need explicit operational choices. Pgvector offers exact search by default, with HNSW for faster approximate search and more index memory/build cost ([pgvector README](https://github.com/pgvector/pgvector#indexing)). Test filtered recall carefully: pgvector explains that approximate index scans apply filters after scanning and may return fewer matches; iterative scans, exact filtered search, partial indexes, or partitioning can help depending on selectivity ([pgvector filtering docs](https://github.com/pgvector/pgvector#filtering)).
4. **Improve candidate quality.** Use dense retrieval for paraphrases and a lexical/full-text path for exact names, IDs, citations, and rare terms; merge candidate lists with reciprocal rank fusion, then rerank a bounded shortlist. This is *lexical + semantic* hybrid search, distinct from Mastra docs' use of “hybrid vector search” for semantic search plus structured metadata filters ([Mastra retrieval guide](https://mastra.ai/reference/rag/retrieval), [pgvector hybrid search](https://github.com/pgvector/pgvector#hybrid-search)). Mastra exposes [`rerank()`](https://mastra.ai/reference/rag/rerank); reranking costs another stage, so evaluate its quality/latency tradeoff.
5. **Add document/section/leaf hierarchy if tests show benefit.** Index short document and section summaries with `documentId`/`sectionId` links. Route a query to candidate documents or sections, retrieve leaf chunks under those IDs, optionally expand to adjacent or parent context, and return the original page citation. Keep a global leaf-search fallback so coarse-stage misses do not become hard failures. This is a proposed design built from Mastra's [RAG primitives](https://mastra.ai/reference/rag/overview) and [metadata filters](https://mastra.ai/reference/rag/metadata-filters), not an advertised built-in parent-child retriever.
6. **Evaluate before increasing complexity.** Create a representative labeled question set, including cross-document questions, exact identifiers, page constraints, recent updates, and no-answer cases. Track retrieval Recall@k, precision/nDCG, citation correctness, answer faithfulness, p50/p95 latency, indexing throughput, and cost at growing corpus sizes. Mastra supports versioned [datasets and experiments](https://mastra.ai/blog/mastra-experiments) and [scorers](https://mastra.ai/blog/mastra-scorers); calculate retrieval metrics separately from answer scores. Compare baseline, filters, ANN, hybrid, reranking, and hierarchy at equal latency/cost budgets.

## Practical conclusion

The document registry, project-scoped filters, PostgreSQL backend, and HNSW index are implemented. The next claim to earn is measured performance: collect a representative literature review question set and compare exact versus HNSW retrieval at increasing chunk counts, with latency and recall reported together. Add hierarchy and GraphRAG only for query sets where they beat simpler retrieval. “Thousands of papers” alone does not establish which index or retrieval structure wins; chunk count, filter selectivity, update rate, and question types determine that choice.
